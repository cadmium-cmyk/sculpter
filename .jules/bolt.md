## 2024-05-24 - Hash Map Collision Performance Bottleneck
**Learning:** For C++ applications doing heavy 3D mesh processing (like Dilay), `std::unordered_map` with `std::pair<unsigned int, unsigned int>` as keys is extremely common (e.g. for caching shared vertices between edge pairs). If the hash function for these pairs uses a simple `hash_combine` approach (like Boost's default), it often leads to high collision rates and $O(N)$ lookup times when edge indices follow regular patterns. Simply packing the bits into a 64-bit integer can cause pathological $O(N)$ clustering on implementations with power-of-two bucket sizes.
**Action:** Always ensure that `std::unordered_map` keys representing coordinate pairs or grid indices utilize a hash function with a robust avalanche effect (e.g. incorporating constants like those in MurmurHash or SplitMix64) to guarantee uniform distribution across buckets regardless of the underlying STL map implementation.
